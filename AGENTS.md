# AGENTS.md — Reinforcement Learning Reto II

This repository is an academic Reinforcement Learning project built around Gymnasium Robotics. This file is the single source of truth for AI coding agents working in the repository.

## Source-of-truth order

When instructions conflict, apply this precedence:

1. `enunciado-reto.md` — academic requirements and evaluation criteria.
2. `lineamientos-transversales.md` — mandatory engineering and delivery rules for the three models.
3. This `AGENTS.md` — repository operating rules for coding agents.
4. DWP v4 plan currently active under `.dwp/plans/`.
5. `Gymnasium_Robotics.ipynb` — technical reference for environment installation and baseline random policies.
6. Model-local README/docs once each model folder exists.

Never silently override a higher-precedence source. If a conflict cannot be reconciled, stop and surface it before implementation.

## Repository goal

Implement three independent Gymnasium Robotics agents:

- `1-AdroitHandDoor/` → `AdroitHandDoor-v1`
- `2-FetchReachDense/` → `FetchReachDense-v4`
- `3-HandReachDense/` → `HandReachDense-v3`

The complete challenge must use at least three distinct allowed RL algorithms and maximize accumulated reward while considering training time and stability.

## Mandatory workflow

- No direct changes to `main`.
- Every substantive change starts on a dedicated branch and reaches `main` through a Pull Request.
- Use Deep Work Plan for substantive engineering work. DWP v4 is Lite-first: create a Lite plan by default and promote to Full only when the scope requires detailed task files.
- `.dwp/` is an operational, gitignored workspace. Do not commit plans or execution state.
- Permanent decisions discovered during a DWP execution must be reflected in tracked documentation when they remain relevant after the plan ends.
- Execute one bounded task at a time; validate before advancing.
- Do not train an expensive model until the repository-specific smoke gates pass.

## Engineering rules

- Prefer the simplest implementation that satisfies the academic requirement and validation gate.
- Apply DRY and SOLID pragmatically; do not introduce abstractions without real duplication or complexity.
- Centralize hyperparameters, seeds and filesystem paths. No duplicated path literals across a model.
- Functions/classes added as reusable Python code use Google-style docstrings.
- Keep notebooks readable: orchestration and narrative belong in the notebook; reusable non-trivial logic may move to a small `src/` module when that materially improves clarity.
- Avoid dead code, speculative infrastructure and production-style MLOps layers not needed for the challenge.
- Use deterministic evaluation mode when the selected algorithm supports it.
- Final evaluation uses at least 10 episodes and is separate from training.
- Each final model must be traceable to the training run documented in its notebook.

## DWP policy

DWP skill release pinned for this repository: `v4.0.0` from `DailybotHQ/deepworkplan-skill`.

Supported repository aliases:

- `#dwp-create <goal>`
- `#dwp-execute`
- `#dwp-status`
- `#dwp-refine`
- `#dwp-resume`
- `#dwp-verify`

These aliases are thin delegators. The installed Deep Work Plan skill is authoritative for lifecycle behavior.

### DWP lifecycle

- Create materializes a plan under `.dwp/plans/PLAN_<slug>/`.
- Lite is the default compact executable representation.
- Full is used when the scope cannot be represented safely as compact task records.
- Promotion Lite → Full preserves stable task identity and completed evidence.
- Guided creation requires approval before execution; `trust`/`auto` may pre-approve when explicitly requested.
- Never execute a pending proposal or a plan with an unresolved promotion state.
- Use machine-readable plan state when generated by DWP; do not hand-edit it except through the DWP lifecycle.

## Validation strategy

The repository is currently notebook-first and does not yet have one universal Python test suite. Do not invent a fake test command. Use the strongest gate available for the surface being changed.

### Harness/documentation changes

```bash
bash -n scripts/bootstrap-dwp.sh scripts/verify-dwp-harness.sh
git diff --check
bash scripts/verify-dwp-harness.sh
```

### Model development

Before long training, validate in this order:

1. dependency install/import;
2. environment `make/reset/step/close`;
3. render/video path;
4. short smoke training;
5. save + reload model;
6. short evaluation;
7. only then full training.

Model-local validation commands must be documented when each model is created.

## Notebook contract

Each model notebook must preserve the chapter structure defined in `lineamientos-transversales.md`:

1. libraries/bootstrap/transversal variables;
2. agent definition;
3. training construction and execution;
4. metrics and three principal plots;
5. videos;
6. technical report.

Do not reorder or remove these major sections without updating the transversal guidelines first.

## Deliverable guardrails

For every model, the final PR must prove:

- clean Colab execution path;
- trained model artifact can be reloaded;
- at least 10 evaluation episodes;
- training time, mean evaluation return ± standard deviation, and success rate;
- three principal plots required by the transversal guidelines;
- `training_process.mp4` with visible reward and `Training Process` title;
- `trained.mp4` with visible reward and trained-agent title;
- report conclusions grounded in produced evidence.
